Bootstrapping

What happens when we run the backend

One command boots the whole stack. Entities let us skip writing DDL — Hibernate generates the schema — but we still seed the data.

Repositories

An interface for reading and writing one entity — we declare the method signatures, Spring Data generates the query and implementation.

public interface CatalogItemRepository
        extends JpaRepository<CatalogItem, String> {

    // Derived query — Spring builds it from the method name, no body.
    // → SELECT * FROM catalog_items WHERE stock < :threshold
    List<CatalogItem> findByStockLessThan(int threshold);

    // Custom query — JPQL for what the name DSL can't express:
    // one atomic, guarded stock decrement.
    @Modifying
    @Query("UPDATE CatalogItem c SET c.stock = c.stock - 1 " +
           "WHERE c.sku = :sku AND c.stock > 0")
    int decrementStock(@Param("sku") String sku);
}

Transactions Layer

Service

Where the business logic lives — orchestrates repositories inside one transaction to complete a checkout.

POST /transactions/{id}/complete
transactions/TransactionService.java
@Transactional
public Map<String, Object> complete(String transactionId) {
    Transaction transaction = find(transactionId);
    if (transaction.getStatus() != OPEN)
        throw CheckoutException.transactionNotOpen(transactionId, transaction.getStatus());

    List<TransactionLineItem> lineItems = lineItemRepository.findByTransactionId(transactionId);
    if (lineItems.isEmpty())
        throw CheckoutException.basketEmpty(transactionId);

    Map<String, List<TransactionLineItem>> bySku = new TreeMap<>();
    for (TransactionLineItem li : lineItems)
        bySku.computeIfAbsent(li.getSku(), s -> new ArrayList<>()).add(li);

    Map<String, CatalogItem> catalog = new LinkedHashMap<>();
    for (CatalogItem item : catalogItemRepository.findAllById(bySku.keySet()))
        catalog.put(item.getSku(), item);

    List<TransactionLineItem> fulfilled = new ArrayList<>(), unfulfilled = new ArrayList<>();
    releaseStock(bySku, fulfilled, unfulfilled);
    if (!unfulfilled.isEmpty())
        lineItemRepository.deleteAllInBatch(unfulfilled);

    transaction.setItemCount(fulfilled.size());
    transaction.setStatus(COMPLETED);
    transaction.setCompletedAt(LocalDateTime.now());
    transactionRepository.save(transaction);
    return Map.of("transactionId", transaction.getTransactionId(),
                  "itemCount", fulfilled.size(),
                  "lines", buildReceiptLines(fulfilled, catalog));
}

Key steps
  1. Validate — transaction exists, is OPEN, basket not empty.
  2. Group line items by SKU in a sorted TreeMap (same lock order ⇒ no deadlock).
  3. Decrement stock per unit via the guarded UPDATE.
  4. Drop units that couldn't be decremented — never billed.
  5. Commit — mark COMPLETED, save, return the receipt.

Analytics Layer

Popular items

GET /analytics/popular-items
analytics/AnalyticsService.java
private static final int WINDOW_SIZE    = 1000;
private static final int SLIDE_INTERVAL = 500;
private final AtomicLong globalScanSeq  = new AtomicLong(0);

public void recordScan(String sku) {
    long seq = globalScanSeq.incrementAndGet();
    scanEventRepository.save(new ScanEvent(seq, sku, LocalDateTime.now()));
    if (seq % SLIDE_INTERVAL == 0 && seq >= WINDOW_SIZE)
        recompute(seq);
}

private void recompute(long currentSeq) {
    List<Object[]> topSkus = scanEventRepository.findTopScannedSkus(WINDOW_SIZE, DEFAULT_LIMIT);
    long windowStart = Math.max(1, currentSeq - WINDOW_SIZE + 1);
    snapshotRepository.deleteAllInBatch();
    int rank = 1;
    for (Object[] row : topSkus) {
        String sku = (String) row[0];
        int count  = ((Number) row[1]).intValue();
        CatalogItem item = catalogItemRepository.findById(sku).orElseThrow();
        snapshotRepository.save(new PopularItemSnapshot(
                windowStart, currentSeq, now, sku, item.getName(), count, rank++));
    }
}

Key steps
  1. Record each scan with a monotonic seq.
  2. Every 500 scans (once past 1000), recompute the window.
  3. Rank the top 10 SKUs over the last 1000 scans.
  4. Snapshot the result — reads become cheap lookups.

Analytics Layer

Tracing the algorithm

  1. Every scan: assign a monotonic seq, persist ScanEvent(seq, sku, now).
  2. Trigger: if seq % 500 == 0 and seq ≥ 1000, recompute.
  3. Aggregate the newest 1000 events: group by SKU, count, order desc, top 10.
  4. Wipe the snapshot table.
  5. Insert one ranked snapshot row per SKU (rank 1…10).
  6. Reads return the latest snapshot — O(k), no aggregation.
The hopping window — size 1000, hop 500

Each window is the newest 1000 scans; a new one is computed every 500, so they overlap by 500.

data/ScanEventRepository.java — findTopScannedSkus()
@Query(value =
    "SELECT recent_scans.sku, COUNT(*) AS scan_count " +
    "FROM (SELECT * FROM scan_events " +
    "      ORDER BY global_seq DESC LIMIT :windowSize) recent_scans " +
    "GROUP BY recent_scans.sku " +
    "ORDER BY scan_count DESC " +
    "LIMIT :limit",
    nativeQuery = true)
List<Object[]> findTopScannedSkus(@Param("windowSize") int windowSize,
                                  @Param("limit") int limit);
Native SQL because JPQL can't put LIMIT inside a subquery. Rows come back as Object[] — [sku, scanCount] — since no entity matches that shape.

Controller

The HTTP entry point that ties it together — maps requests to methods, validates input, and delegates to a service. No business logic here.

@RestController
public class CheckoutController {

    private final TransactionService transactionService;
    private final AnalyticsService analyticsService;

    public CheckoutController(TransactionService transactionService,
                              AnalyticsService analyticsService) {
        this.transactionService = transactionService;
        this.analyticsService = analyticsService;
    }

    @PostMapping("/transactions/{transactionId}/items")
    public Map<String, Object> addItem(@PathVariable String transactionId,
                                       @Valid @RequestBody ScanItemRequest request) {
        return transactionService.scan(transactionId, request.sku());
    }

    public record ScanItemRequest(@NotBlank String sku) {}
}

The change that mattered most

Index on transaction_line_items(transaction_id):
+20% tx/s · COMPLETE p50 14.83 → 5.61 ms · rows scanned 2.5 B → 0.

Why: complete() runs findByTransactionId on every checkout. Without the index, Postgres scans a table that grows all run — O(n). The index makes each lookup a direct seek.
Reflections

Trade-off analysis

Architectural

DecisionBenefitCost
Package-by-layerClear, testable seamsMore structure than a monolith
Entities as responses (no response DTOs)Much less codeWire tied to schema
DB persistence for all stateOne source of truth, survives interruptionsEvery op is a DB round-trip
Layering itself was essentially free — the pure refactor measured 364 vs 368 tx/s, within noise.

Business logic

DecisionBenefitCost
Guarded atomic UPDATECorrect, no locksLogic split app / DB
Snapshot precomputeO(k) reads — just the ~10 stored rowsStale ≤ 500 scans (rebuilt every 500)
Enforce stock invariantNever over-sell−1.6% throughput
Meets the contract — 7 endpoints, exact schemas, non-negative stock, window 1000 / 500.
Reflections

Challenges & next steps

Challenges

  • Identifying the bottleneck — pinning down what actually capped throughput (an index, not CPU or the pool).
  • Deciding which business logic to enforce — which invariants are worth their cost; we chose stock correctness.
  • Over-selling found in Week 1 — inspecting the prior code, out-of-stock units were counted as sold: the stock > 0 guard keeps stock from going below 0, so those units were never decremented yet stayed on the bill (initial − final ≠ sold). Took time to work out a fix — drop unfulfilled units at completion — and it still isn't perfect (the shopper has the item in hand).
How we hold it: units we can't decrement are dropped at completion, so initial − final == sold. Real-world caveat: the shopper already holds the item — silently dropping it from the bill isn't realistic; production would reconcile (substitute / override).

If we had more time

  • Find the real database limit — throughput flattens ~537 tx/s; locate the next ceiling.
  • Add response DTOs — we have request DTOs (the records); responses still return entities.
  • Async analytics — move recordScan off the scan path.
